# 管理ポータル

同じLAN内の端末で管理サーバーを開きます。以下の192.0.2.10は説明用です。実際のIPに置き換え、初期構築ガイドに従って内部CAを信頼してください。

配信アプリも `https://192.0.2.10:18001` のようにHTTPSを使用します。以前のHTTPリンクはHTTPSへ変更してください。アプリのHTTPポートはサーバー内の127.0.0.1だけで待ち受け、Caddyが同じ公開ポートでTLSを処理します。新規配置時もHTTPS経路を自動追加します。管理ポータルのセッションCookieはアプリへ転送しません。

## ログイン

端末用認証キーを入力します。Windowsセットアップ後は `%LOCALAPPDATA%\LocalSites\device.token` に保存されています。内容をローカルでコピーしてログイン欄に貼り付けてください。キーをチャットやURLに貼り付けないでください。

セッションは8時間で失効します。ログアウト、管理サービスの再起動、端末用キーの失効でも使用できなくなります。キーはブラウザーのlocalStorageやURLに保存せず、Secure / HttpOnly / SameSite=Strict Cookieを使用します。変更操作はOriginとCSRFトークンを検証します。ログイン試行制限は管理サービスから見た接続元単位です（現在のリバースプロキシ構成では端末間で共有されます）。

## 操作

- 上部の「サーバー」「アプリ」で画面を切り替えます。タブはスクロール中も表示されます。アプリ画面にはサーバーのCPU・メモリ・ディスクの小さな概要と警告を表示します。
- `https://portal.home.arpa/#server` と `https://portal.home.arpa/#apps` をブックマークできます。再読み込み・ログイン後も指定画面を開き、ブラウザーの戻る・進むでも切り替えられます。初期表示・不明な指定はサーバー画面です。
- タブにフォーカスして左右矢印で切り替え、Homeでサーバー、Endでアプリへ移動できます。「本文へ移動」は現在の画面へキーボードで直接移動します。非表示の画面は読み上げとTab移動の対象から外れます。
- タブの切り替えでは検索・並べ替え・グラフ期間・各画面のスクロール位置を保持します。これらの操作状態は同じページ内で保持し、ページ自体の再読み込みでは画面の指定以外は初期値に戻ります。
- 自動更新で操作位置を移動させず、通常の数値更新は読み上げを繰り返しません。注意状態の変化を通知します。非表示のグラフ描画は省略しますが、サーバーの計測・履歴保存は継続します。
- 一覧は30秒ごとに更新します。「更新」でも再取得できます。
- 「開く」は別タブでアプリを表示します。アプリ自体の認証は従来のままです。
- 「停止」はコンテナとデータを残します。「起動」で再開できます。
- 「削除」はコンテナを削除し、保存データ・アプリID・URLを残します。削除済みとして一覧に表示され、同じIDで再配置するとデータを再利用できます。
- 「完全削除」は対象名の入力後にコンテナ・保存ボリューム・アプリ登録を削除します。元には戻せません。ポート予約も解除されます。
- ビルド済みイメージと過去の配置履歴は完全削除でも保持します。
- ログ・URLコピー・削除・完全削除は、カードの「その他の操作」から開きます。
- 削除中にボリューム削除が失敗した場合、削除済みレコードが残ります。原因解消後に完全削除を再試行できます。

## 会話からの操作

プラグインは `get_portal_url` と `delete_app` を追加しています。新しいタスクで「Local Sites の管理ポータルを開いて」「アプリ一覧を表示して」と依頼できます。通常の削除はデータ保持が既定です。保存データまで消すには完全削除を明示してください。

プラグインの詳細リンクは公開リポジトリです。実際の管理ポータルURLは `get_portal_url` で取得します。

## 検証

`npm test` で認証・失効・CSRF・削除の所有確認・配置中の拒否・データ保持・完全削除失敗時の記録を検証します。

実機確認では使い捨てアプリを用い、保存データの復帰とURLを確認してください。公開版での検証範囲は [検証結果](verification-ja.md) を参照してください。

## リソース監視

ダーク基調のダッシュボードで、サーバータブに全体の概要と推移、アプリタブにアプリごとのリソースを表示します。「リソース詳細」で各アプリのグラフを開けます。名前検索とCPU・メモリ・保存容量の降順に対応します。

- CPUはホスト全コア合計を100%、アプリは実際の割り当て上限を100%とします。アプリの既定上限は1コアです。
- ホストのメモリ使用量は総容量からMemAvailableを引いた値です。アプリはDocker統計から再利用可能なファイルキャッシュを除外し、実際のメモリ上限と比較します。既定上限は512MiBです。
- ディスクはOSとDockerのボリューム保存領域を確認し、同じファイルシステムはまとめます。使用率はLinuxのdfと同様に使用量÷（使用量＋利用可能容量）で求めます。予約領域があるため、表示の総容量と使用量＋空き容量は一致しないことがあります。
- ネットワークはLANインターフェースの受信・送信速度です。アプリ側はそのコンテナの通信速度で、ホストの値との合計・差分は取りません。B/s、KiB/sなど、1024単位を使用します。
- アプリの保存容量は /data の永続ボリューム使用量です。コンテナのイメージ、書き込みレイヤー、ログは含みません。5分間隔で別途計測し、取得時刻を表示します。

画面を閉じても30秒ごとに計測します。表示期間は1時間（30秒単位）・24時間（5分単位）・7日（15分単位）。実線は平均、薄い破線はピークです。各グラフのスライダーは矢印キーで時刻と数値を確認できます。複数系列のグラフ上部の平均・最大は最初の系列（通信量は受信）です。導入以前の履歴はありません。

取得できない値は「—」、履歴は欠測として表示します。停止中・削除済みのCPUなども欠測にし、保存容量と過去の履歴は確認できます。完全削除したアプリは一覧・履歴APIの対象から外れ、記録ファイル内の古いリソース値は保存期限で消えます。

CPUまたはメモリが85%以上で3分継続した場合は注意、95%以上で3分継続した場合は重大表示になります。95%をまたぐ変動中も85%以上の継続判定は維持します。ディスクは85%・95%で即時判定。収集の欠測・90秒超の中断で継続判定をリセットします。最新ホスト値が90秒以上古いと更新遅延、保存容量が10分以上古いと容量の更新遅延を表示します。外部への通知や自動停止はしません。

## 計測の設定と復旧

Composeではホストの `/proc` を `/host/proc`、`/` を `/host/root` に読み取り専用でマウントします。ホストネットワークと既存のDockerソケットを利用します。ホスト通信はSITE_IPに対応するインターフェースを優先し、見つからない場合は既定経路を使用します。固定する場合は `deploy/.env` の `METRICS_NETWORK_INTERFACE=eno1` で指定できます。サーバー側の独自配置では `METRICS_HOST_PROC` と `METRICS_HOST_ROOT` を変更できます。

履歴は `/var/lib/local-sites/metrics/YYYY-MM-DD.jsonl` へ記録し、画面には直近7日分だけを返します。完全に期限を過ぎた日別ファイルを削除するため、境界の日のファイルは最大1日余分に残ります。再起動時は正常な行を復元し、中断された行は無視します。履歴の読み書きに失敗してもアプリ管理は継続します。ディスクの空き・書き込み権限、管理コンテナのログを確認してください。

認証済みの読み取り専用APIは `GET /api/metrics/current` と `GET /api/metrics/history?range=1h|24h|7d&appId=任意の登録ID` です。appIdを省略するとホストの履歴を返します。管理ポータルと同じセッション認証を使用し、MCPの道具は変更していません。

更新・バックアップ・復旧は [運用ガイド](operations-ja.md) を参照してください。
